\section{General architecture}

The platform is organized into four main components, communicating over HTTP APIs:
\begin{itemize}
\item a \textbf{frontend} built with Next.js, offering three distinct spaces depending on the role (Administrator, Head Technician, Technician);
\item a \textbf{backend} built with FastAPI, responsible for business logic, data persistence (PostgreSQL), and security (authentication, access control);
\item a \textbf{Machine Learning microservice} built with Flask, in charge of serving the predictive models (P1 to P7);
\item a \textbf{RAG service}, in charge of document ingestion and generating conversational responses enriched with real-time ML context.
\end{itemize}

The whole system is orchestrated by Docker, with object storage (MinIO) for documents and attachments.

\section{Machine Learning pipeline architecture}
\label{sec:ml-pipeline-architecture}

\subsection{Problem framing and maintenance strategy}

Industrial equipment fails along a degradation curve that is, in most cases, measurable long before the failure itself becomes visible. Three maintenance strategies exist. \textbf{Reactive maintenance} waits for failure before acting: unplanned downtime, emergency parts orders, and production losses are its defining characteristics, and it represents the worst operating mode in terms of total cost. \textbf{Preventive maintenance} acts on a fixed calendar, replacing components that may still have significant life remaining while missing failures that occur between scheduled intervals. \textbf{Predictive maintenance} is the target of this platform: it uses sensor data and ML models to estimate when a machine will fail, which failure type is developing, and what parts will be needed, and it does this before the failure occurs, so that maintenance can be triggered at the right moment rather than too early or too late.

The core question every component of the ML service is designed to answer is: \emph{given a machine's current sensor readings and history, how healthy is it right now, how long before it needs intervention, and what should the team prepare?}

\subsection{Training data: the AI4I 2020 dataset}

All predictive models are initially trained on the AI4I 2020 Predictive Maintenance Dataset, a publicly available UCI benchmark that simulates CNC machine operations. The dataset contains 10\,000 machine cycle records across 100 simulated machines, with a failure rate of 3.4\% (339 confirmed failure events distributed across five failure types). It provides the supervised signal needed to train classification and regression models before any real machine-specific history is available.

Each cycle is described by five sensor readings and two derived features:

\subsection{Data quality and validation methodology}

Before any model is trained, four data quality constraints are enforced.

\paragraph{Synthetic data quarantine.}
Every seeded or generated telemetry row is flagged \texttt{is\_synthetic = true} at write time. The ML service filters these rows out by default in production (\texttt{ML\_ALLOW\_SYNTHETIC\_TELEMETRY = false}), so models only consume readings that come from real sensors. Synthetic data remains available only for local pipeline testing through an explicit environment flag.

\paragraph{Null telemetry handling.}
If a machine has no real telemetry on record, the system does not substitute placeholder sensor values. Calling an ML model on fabricated inputs would produce a prediction that looks valid but is entirely meaningless. Instead, the service returns \texttt{telemetry\_available: false}, skips the microservice call, and falls back to a simpler rule-based health estimate derived from maintenance history alone.

\paragraph{Label leakage detection.}
The most significant data quality issue found during development was \emph{target leakage}: the training labels for P1, P2, and P5 were generated by deterministic formulas of \texttt{tool\_wear}, the same feature the models read as input. A model trained on such data learns to reproduce the formula, not to predict real failures. These models report near-perfect accuracy figures in validation ($\sim$99\% AUC-ROC) but the number measures arithmetic reproduction, not predictive power. They are tagged \texttt{validation\_status: "leaked"} in the model registry, and their accuracy figures are suppressed in the dashboard. Fixing this requires replacing the formula-derived labels with real, technician-confirmed failure records.

\paragraph{Group-holdout validation.}
For time-series machine data, a random 80/20 row split is unsound: both sets contain readings from the same machines, which means the model sees data from a machine's own degradation trajectory in both training and test. This inflates test scores by memorisation rather than generalisation. The correct procedure is to hold out entire machines during training (for example, withholding machines with IDs 70--79 entirely) so that evaluation is always performed on machines the model has never encountered. This is the methodology used for P3, and it is the reason its validation metrics are considered reliable while the others' are not.

They are trained separately and never consume one another's output: each reads the same shared telemetry feature set from Table~\ref{tab:features} and returns its own field in the unified API response.

\paragraph{P1: Failure Probability.}
An XGBoost binary classifier that outputs a 0--100\% probability of failure within the next cycle. Its primary role is to rank machines by urgency so that planners inspect the highest-risk ones first. As discussed in Section~\ref{sec:validation}, this model's accuracy figure is not a reliable measure of real predictive power due to label leakage.

\paragraph{P2: Failure Type Classification.}
A multi-output XGBoost classifier that predicts which failure mode is developing among five possibilities: tool wear failure (TWF), heat dissipation failure (HDF), power failure (PWF), overstrain failure (OSF), and random failure (RNF). Its output allows maintenance teams to pre-stage the correct spare parts and skill set before a technician arrives, reducing intervention duration.

\paragraph{P3: Remaining Useful Life Estimation.}
An XGBoost regressor that estimates how many operational cycles remain before the machine requires intervention. It is the only model in the pipeline with a validated, non-leaked signal: after switching from a random row split to group-holdout validation (machines 70--79 withheld entirely from training), the model achieves a mean absolute error of 14.95 cycles and a concordance index of 0.620. A quantile regression head trained alongside the point estimator provides a calibrated prediction interval (P10 to P90), so the dashboard displays a range rather than a single number, reflecting the true uncertainty in the estimate.

\paragraph{P4: Behavioral Anomaly Detection.}
A four-method ensemble that detects abnormal sensor behaviour. Isolation Forest contributes 30\% of the combined score, Z-Score normalization 20\%, cluster deviation 10\%, and a trained neural autoencoder 40\%. The ensemble score is normalized to $[0,1]$; a score above 0.5 is classified as an anomaly. Using TensorFlow CPU, the autoencoder was trained exclusively on failure-free machine cycles and a separate \texttt{.keras} artifact is loaded at startup alongside the classical methods.

\paragraph{P5: Work Order Priority.}
An XGBoost classifier that assigns a priority level (LOW, MEDIUM, HIGH, CRITICAL) to a predicted failure, allowing the maintenance scheduler to sequence the work queue. Like P1, its labels in the current training set are derived from the same sensor features, making its accuracy figure unreliable until real priority judgements from technicians are accumulated.

\paragraph{P6: Maintenance Scheduling.}
An XGBoost classifier that recommends the appropriate scheduling window: immediate, within the week, or planned. It enables the platform to distinguish between a machine that needs intervention today and one that can be included in the next scheduled maintenance cycle without risk.

\paragraph{P7: Parts Demand Forecasting.}
A statistical forecasting module that predicts which spare parts will be needed and when. It combines survival analysis (estimating the probability that a machine will require each part within a future window) with Croston's method for intermittent demand forecasting (suited to parts that are replaced in occasional bursts rather than steadily). When forecast demand exceeds current stock, a shortage alert is raised and a draft procurement request is generated for human approval.

\subsection{Wave 2 signal processing models}

A second, parallel pipeline (referred to as Wave 2) processes each machine's telemetry \emph{history} rather than a single snapshot. Four signal-processing models run concurrently:

\begin{itemize}
\item a \textbf{Physics-Informed Neural Network (PINN)} that encodes degradation physics as soft constraints in the loss function, preventing the model from producing physically impossible RUL estimates;
\item a \textbf{Cox Proportional Hazards survival model} that estimates the probability of failure over a future time window while explicitly handling right-censored machines (those still running at the observation cutoff, whose future fate is unknown);
\item a \textbf{Mahalanobis Health Index} that measures how far current sensor readings deviate from that specific machine's own healthy baseline, excluding the tool-wear reset event from computation to avoid false alarms immediately after a tool replacement;
\item a \textbf{CUSUM anomaly detector} smoothed by a \textbf{Kalman filter} to detect slow cumulative drift that point-in-time snapshots miss.
\end{itemize}

\subsection{Dempster-Shafer evidence fusion}

The outputs of the Wave 2 models are combined through Dempster-Shafer evidence theory (DST), a mathematical framework for combining uncertain, potentially conflicting evidence from independent sources. The frame of discernment is $\Theta = \{\mathrm{Healthy},\, \mathrm{Degrading},\, \mathrm{Critical},\, \mathrm{Unknown}\}$.

Each model converts its output into a \emph{Basic Probability Assignment} (BPA) over $\Theta$ using piecewise-linear membership functions. A model with high confidence contributes most of its mass to one of the three substantive hypotheses; a model that is unavailable or disagrees strongly with the others contributes its mass to \textit{Unknown} rather than distorting the combined estimate. The combination rule switches between Dempster's rule (when conflict $K \leq 0.8$) and the more conservative Yager's rule (when $K > 0.8$), so that genuine disagreement between sources is reported as uncertainty rather than silently overridden.

This mechanism is important for the platform's credibility. A system that always produces a confident-sounding answer, even when its own inputs contradict one another, will eventually be confidently wrong. The DST layer is designed to say ``not sure yet'' explicitly, rather than forcing a false consensus. The fused BPA yields the single \emph{unified health score} (0--100) and an overall verdict that downstream readiness and alerting logic consumes.

In everyday terms, the four boxes at the top of Figure~\ref{fig:wave2-explainer} can be read as follows.

\textbf{Drift watch} keeps an eye on whether a machine's readings are slowly creeping away from normal, cycle after cycle. A single unusual reading is not a concern; a small change that keeps growing, day after day, is. This is the one signal built specifically to catch that kind of slow, easy-to-miss decline before it turns into a sudden breakdown.

\textbf{Distance from normal} compares a machine's current readings against its own personal baseline: what "normal" looks like for that specific machine, not for machines in general. The further today's reading sits from that baseline, the more it stands out. A recent tool change is deliberately ignored for a short while after it happens, so that a routine part swap is never mistaken for a warning sign.

\textbf{Survival odds} asks a different question: given everything known about similar machines, how long do machines like this one typically keep running before needing attention? Importantly, it does not only look at machines that have already broken down; it also learns from every machine that is still healthy and running today, which is what makes its estimate of "how long is left" meaningfully more honest.

\textbf{Physics check} acts as a common-sense filter on top of the other estimates. It knows the basic physical rules a machine has to obey (for instance, that remaining lifetime cannot suddenly jump up for no reason) and it rejects any estimate that breaks those rules, even if a purely statistical model would have accepted it.

Together, these four signals are combined by the fusion step: when they broadly agree, the platform reports a confident health score; when they clearly disagree with each other, it says so honestly instead of picking a number at random, as illustrated in the bottom half of Figure~\ref{fig:wave2-explainer}.

\subsection{Live inference request flow}

When a user opens a machine detail page, the following sequence executes:

\begin{enumerate}
\item The frontend requests \texttt{GET /api/v1/ml/machines/\{id\}/unified-health}.
\item The backend queries PostgreSQL for the latest real sensor readings, filtering out synthetic rows. If none exist, it returns \texttt{telemetry\_available: false} and stops here.
\item The backend posts the sensor snapshot to the ML microservice, which runs P1--P7 in parallel (models are held in memory via an LRU cache after first load to avoid re-reading disk on every request).
\item The Wave 2 models process the telemetry history concurrently.
\item The DST fusion layer combines all available signals into the health score and verdict.
\item The complete prediction record is written to \texttt{ml\_prediction\_logs} for audit and future retraining.
\item The response is returned to the frontend, which renders the ML Intelligence panel.
\end{enumerate}

\subsection{Downstream processing: readiness, alerts, and procurement}

The readiness score blends the unified health score (40\%) with inventory coverage (30\%), procurement risk (20\%), and maintenance recency (10\%). Alerts aggregate signals from both pipelines (an anomaly flag from P4, a parts shortage from P7, or a model-disagreement flag from the fusion step itself) and a detected parts shortage triggers the purchase draft, as shown in Figure~\ref{fig:downstream}.

\begin{figure}[h]
\centering
\includegraphics[width=0.85\textwidth]{figures/downstream.png}
\caption{From ML outputs to readiness, alerts, and purchase drafts}

P7 acts as a smart shopping list rather than an automated buyer. Every spare part is consumed at its own pace (some wear steadily, others are only replaced in occasional bursts) and P7 learns that pace per part, per machine, then combines it with how likely each machine is to need work soon. From this it estimates how many units of a given part will be needed within the coming weeks, and compares that estimate against what is actually available in the warehouse. When the numbers do not add up, a shortage alert is raised well before a technician is left waiting for a part in the middle of a repair. The system never places an order autonomously; it only prepares the suggestion, and a human must review and approve it.

\section{RAG service and ML bridge architecture}

The RAG service ingests technical documentation (maintenance manuals, safety procedures, machine data sheets) and splits it into indexed fragments for semantic search. When a technician asks a question about a specific machine, the backend queries the RAG service (documentation) and the ML microservice (the machine's real-time health status) in parallel, then merges the two contexts before passing them to the language model to generate a response, as shown in Figure~\ref{fig:rag-bridge}. This mechanism ensures the assistant always responds, even if one of the two services is unavailable.

\section{End-to-end request flow}

Figure~\ref{fig:architecture} shows the components involved; the sequence below walks through a single request, from the user's action to the answer returned, in order:

\begin{enumerate}
\item \textbf{User to Backend}: a technician asks a question in the chat, or an administrator uploads a document. Either way, the request first lands on the FastAPI backend.
\item \textbf{Backend to RAG Service}: the backend forwards the request to the RAG microservice: an upload becomes an ingest call, a question becomes a retrieve call.
\item \textbf{RAG Service to PostgreSQL}: the RAG microservice performs its ingest/embed or retrieve/rerank work directly against PostgreSQL with pgvector, writing new chunks and vectors on ingest, reading and ranking them on retrieve.
\item \textbf{RAG Service to MinIO}: in parallel, the RAG microservice stores the original uploaded file in MinIO, or reads it back for a download.
\item \textbf{Backend to Groq LLM}: for a question, the backend takes the retrieved context back from the RAG service and hands it to the Groq-hosted language model.
\item \textbf{Groq LLM to User}: the language model generates the answer from that context, and the backend returns it to the user.
\end{enumerate}

\section{Technology choices}

\begin{itemize}
\item \textbf{Next.js}: hybrid rendering, mature React ecosystem, well suited to rich, role-based interfaces;
\item \textbf{FastAPI}: high performance, native schema validation, automatically generated API documentation;
\item \textbf{Flask}: lightweight, well suited to a model-serving microservice;
\item \textbf{PostgreSQL}: transactional robustness, relational queries well suited to the data model;
\item \textbf{Docker}: isolation and reproducibility of development and deployment environments;
\item \textbf{MinIO}: S3-compatible, self-hostable object storage.
\end{itemize}
