# Phase 2a SAST (Semgrep) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add Semgrep-based SAST as a new blocking CI stage (3 jobs: auto-config, explicit rulesets, project-custom rules) covering all 4 EAM services, closing the gap where in-house code and the ml-microservice/rag-service directories had zero security scanning.

**Architecture:** New `sast` stage inserted between `sca-deps` and `lint` in both `.gitlab-ci.yml` and `.github/workflows/source-security.yml`. Three parallel jobs (`sast-auto`, `sast-explicit`, `sast-custom`) each scan all 4 service directories and gate on WARNING/ERROR severity findings. Custom rules live in a project-owned `.semgrep/custom.yml`, developed test-first using Semgrep's built-in `--test` framework (ruleid/ok annotations in fixture files).

**Tech Stack:** Semgrep CLI (`pip install semgrep`), Semgrep Registry rulesets (`p/owasp-top-ten`, `p/python`, `p/typescript`), GitLab CI, GitHub Actions, `github/codeql-action/upload-sarif@v3`.

## Global Constraints

- Spec: `docs/superpowers/specs/2026-07-03-sast-phase2-design.md`
- Pipeline stage order: `secret-scan → sca-deps → sast → lint → gate` (exact — do not reorder)
- Job names, exact: `sast-auto`, `sast-explicit`, `sast-custom`
- Blocking rule: `--severity WARNING --severity ERROR` findings fail the job; `INFO` findings do not
- Scan targets, exact 4 dirs: `app/backend app/frontend app/ml-microservice app/rag-service`
- Timeout: 10 minutes per SAST job (matches existing `sca-deps` jobs)
- Blocking tier: `allow_failure: false` (GitLab) / no `continue-on-error` (GitHub) — same tier as `scan-secrets`/`audit-backend`/`audit-frontend`
- Branch rules: identical to existing jobs — `clean_Phase_1`, `Phase_1`, `main`, plus MR (GitLab) / PR (GitHub) events
- Suppression mechanisms: inline `# nosemgrep: <rule-id>` (Python) / `// nosemgrep: <rule-id>` (JS/TS) with a reason comment, and `.semgrepignore` for path exclusions
- No Semgrep account/API token required or used for Tasks 1-9 (`sast-auto`, `sast-explicit`, `sast-custom`) — `--config auto` and registry configs (`p/...`) are fetched anonymously. **Exception:** Task 10 (added post-approval, user request 2026-07-03) adds a 4th job, `sast-appsec-platform`, using `semgrep ci` with a `SEMGREP_APP_TOKEN` secret — this is a deliberate scope addition to the original spec, not a contradiction to resolve.

- [ ] **Step 4: Add the rule**

```yaml
# .semgrep/custom.yml
rules:
  - id: sqlalchemy-raw-sql-interpolation
    languages: [python]
    severity: WARNING
    message: >-
      SQL query built via string interpolation instead of bound parameters.
      Use SQLAlchemy's parameter binding (`:name` placeholders + a params
      dict) instead of f-strings, `.format()`, or `%` to avoid SQL injection.
    metadata:
      category: security
      cwe: "CWE-89: Improper Neutralization of Special Elements used in an SQL Command"
      references:
        - https://owasp.org/www-community/attacks/SQL_Injection
    patterns:
      - pattern-either:
          - pattern: text(f"...")
          - pattern: text("..." % ...)
          - pattern: text("...".format(...))
```

- [ ] **Step 5: Run test to verify it passes**

Run: `semgrep --test --config .semgrep/custom.yml .semgrep/tests/sqlalchemy_raw_sql.py`
Expected: PASS — `1/1 rule` matched correctly, 0 failures.

If it fails because the f-string pattern doesn't match, adjust the `pattern-either` list (Semgrep's f-string ellipsis matching can be picky across versions) and re-run until green before moving on.

- [ ] **Step 6: Commit**


- [ ] **Step 1: Manual — create Semgrep AppSec Platform account + token (user action, not automatable)**

Documented here for the user to follow when ready:
