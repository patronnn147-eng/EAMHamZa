Step 01 — Problem Definition

Why do machines fail when no one expects it?

Industrial machinery runs continuously. Without visibility into degradation, failures happen at the worst possible time — during production, with no spare parts, and no technician ready.

Reactive maintenance

Wait & Fix

Machines run until failure. Unplanned downtime, emergency parts orders, production losses. The worst operating mode.

Preventive maintenance

Fixed Schedule

Parts replaced on a calendar. Wasteful — replacing components that still have life left, missing failures that happen between intervals.

Predictive maintenance ← our goal

Predict & Act

Use sensor data to estimate when a machine will fail, what type of failure, and what parts are needed — before it happens.

The core question the ML service answers

Given a machine's current sensor readings and history, how healthy is it right now, how long before it needs intervention, and what should the maintenance team prepare?

Step 03 — Data Cleaning & Validation

Removing what shouldn't be there

Not all data is usable for training. Synthetic data generated by formulas, null telemetry rows, and incorrectly labelled samples must be handled before any model sees the data.

01

Quarantine synthetic data

Every seeded/generated telemetry row is flagged is_synthetic = true. By default, the ML service filters these out (ML_ALLOW_SYNTHETIC_TELEMETRY=false). Models only learn from real machine readings in production. Synthetic data stays useful only for pipeline testing.

02

Handle missing telemetry gracefully

If a machine has zero real telemetry readings, the system doesn't hallucinate predictions. Instead it returns telemetry_available: false, skips the ML microservice call entirely, and falls back to a simpler rule-based health estimate based on maintenance history alone.

03

Detect label leakage

The most important data quality issue: P1, P2, and P5's training labels were generated by deterministic formulas of tool_wear, the same sensor the models read as input. This creates target leakage — the model learns the formula, not real failure patterns. These models are tagged validation_status: "leaked" and their accuracy numbers are not reported as real performance.

04

Group-holdout validation (not random split)

For time-series machine data, a random 80/20 split is dangerous — the model can see data from the same machine in both train and test, which makes it memorise trajectories. The correct method is to hold out entire machines (e.g. IDs 70–79) from training. This forces the model to generalise to machines it has never seen.

⚠ Honest status on P1/P2/P5 accuracy numbers

These models report ~99% AUC-ROC but this measures arithmetic reproduction, not failure prediction. The high number is caused by label leakage, not good modelling. The dashboard marks these as leaked and does not show accuracy figures for them. This is intentional.

Step 04 — Model Training

Seven specialised models, each answering one question

Rather than one monolithic model, the system trains a specialist for each dimension of machine health. Each model is gated — it must pass a minimum accuracy threshold before it's allowed into production.

Step 05 — Evidence Fusion (Wave 2)

Combining seven signals into one health score

Individual models can disagree. The DST fusion layer combines all signals using Dempster-Shafer Evidence Theory — a mathematical framework for reasoning under uncertainty and partial disagreement.

How DST fusion works

1

Convert to Basic Probability Assignments

Each model's output is converted to a probability mass over four states: Healthy, Degrading, Critical, Unknown. A model with high confidence contributes more; an unavailable model contributes all mass to Unknown (vacuous BPA).

2

Measure conflict (K value)

Dempster's rule works well when models mostly agree. If conflict K > 0.8, the system switches to Yager's conservative rule, which shifts mass toward Unknown rather than forcing a false consensus from contradictory evidence.

3

Combine & produce verdict

The fused BPA yields a final verdict: Healthy / Degrading / Critical / Unknown. The dominant state maps to the 0–100 health score shown on the dashboard.

Wave 2 additional signals

CUSUM + Kalman Filter

Detects cumulative drift and tracks state evolution over time. Catches slow degradation that point-in-time models miss.

Mahalanobis Health Index

Measures how far current sensor readings deviate from the machine's own healthy baseline. Excluded during tool-replacement events to avoid false alarms.

Cox Proportional Hazards

Survival model that estimates the probability of failure over a future time window, explicitly handling right-censored machines (still running at observation cutoff).

PINN RUL Estimator

Physics-Informed Neural Network — embeds degradation physics as soft constraints in the loss function so the model doesn't produce physically impossible RUL estimates.

# Simplified view of how DST fusion combines model outputs

Frame: Θ = { Healthy, Degrading, Critical, Unknown }

Each model output → Basic Probability Assignment (BPA)
m(Healthy) = f(health_index / 100) # grows as HI → 100
m(Degrading) = 1 − |health_index − 50| / 50 # triangle, peak at HI=50
m(Critical) = 1 − health_index / 100 # grows as HI → 0
m(Unknown) = 1 − confidence # uncertainty mass

Combine:
if K ≤ 0.8 → Dempster's rule # standard combination
if K > 0.8 → Yager's rule # excess conflict → Unknown

Output: unified_health_score (0–100) + dst_verdict + BPA beliefs
Step 06 — System Architecture

How the services talk to each other

The ML pipeline is split across two services: a FastAPI backend that orchestrates everything, and a dedicated Flask ML microservice that runs the models in isolation.

Live request flow — step by step

1

Frontend requests machine health

The MLIntelligenceTab component calls GET /api/v1/ml/machines/:id/unified-health when a user opens a machine detail page.

2

Backend fetches telemetry

The backend reads the latest real sensor readings from PostgreSQL. If no real readings exist (is_synthetic filtered out), it returns telemetry_available: false and skips the ML call entirely.

3

ML microservice runs all models

The backend POSTs to the ML microservice with the sensor readings. The microservice runs P1–P7 in parallel (models loaded in memory via lru_cache), plus the Wave 2 signals, and returns all predictions.

4

DST fusion combines the signals

The backend applies Dempster-Shafer fusion to all available model outputs, resolving conflicts and producing the unified_health_score, dst_verdict, and BPA belief distribution.

5

Shadow log persisted

The complete prediction (all P1–P7 outputs + DST result + sensor readings) is written to ml_prediction_logs for audit, PDCA analysis, and future retraining.

6

Response returned to frontend

The frontend receives a rich JSON payload with health score, RUL interval, anomaly status, parts demand, and alert flags — rendered as the ML Intelligence panel.

What real data unlocks

→

Technician-confirmed failure records

When a technician closes a work order and marks the root cause (TWF / HDF / PWF / OSF / RNF), that's a label P1 and P2 can actually learn from — not a formula. 1,000+ events over 6–12 months is the minimum viable dataset.

→

Real run-to-failure sequences for P3

15–20 machines tracked continuously from healthy state to confirmed failure (or planned decommission). This gives P3 real censored sequences to learn from, unlocking Cox / Weibull survival models as the next architecture step.

→

Vibration + motor current sensors

The single highest-value hardware investment. Bearing degradation, the most common industrial failure mode, is invisible in air/process temp + torque. Vibration RMS/kurtosis and motor current draw are the signals that make P1/P3/P4 genuinely powerful.

Summary

The complete journey, in one view

What the platform does today

Collects machine telemetry, runs 7 models + 4 Wave-2 signals, fuses them with evidence theory, surfaces a health score and parts demand forecast — all in real time per machine.

What's still limited
